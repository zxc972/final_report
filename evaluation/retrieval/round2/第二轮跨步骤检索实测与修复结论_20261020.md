# 第二轮图文检索实测：完整流程、代码证据与证据打包（2026-10-20）

**本轮已完成 24 个主实验回答和 8 个诊断回答，共 57 次真实 API 请求。** 新增了完整教程段落和固定提交的源码，并测试了多查询、父段落检索。结果仍不支持把 LightRAG mix 直接设为默认最优方案；本轮具体找到了图文联合检索漏证据、片段级条件丢失和流程归属混淆三个问题。下一步可以围绕这些明确问题修改检索服务，不需要再次推倒重建整张图。

## 二、主实验怎样比较

模型、嵌入和 LightRAG 版本沿用首轮：deepseek-v4-pro、BGE-small-en-v1.5 384 维、LightRAG 1.5.7。密钥仍只在服务器。

- 原生 naive 与原生 mix 各检索一次，保存实际返回内容。
- 新的 6 个问题在本轮 API 调用前冻结：5 个需要跨段/跨步骤的信息问题，1 个缺少队列依据、应拒绝给出数值的问题。
- 两组回答上下文的总上限均为 **1,800 个 o200k token**，包含序列化元数据。mix 预留部分给图节点和边，因此原文上限为 1,450；这是一种明确的资源分配配置，不是唯一合理设置。
- 检索参数：实体/关系候选 top_k=8，最终片段最多 4 个；不使用 reranker。每个原文片段单独附来源范围，避免版本信息只在文档开头出现。
- 每份固定检索上下文生成两次答案，共 24 个回答。它们是回答稳定性重复，**不是两次独立索引或独立检索实验**。
- 两组使用相同结构化回答提示词，要求区分事实、条件、例外和未确定事项；评审目标及正确来源清单不进入模型。

实际上下文平均 naive 1,155 token、mix 1,778 token，虽然上限相同，实际长度仍不相等。与首轮相比，语料、问题、上下文配置和回答格式均有改变，不能用两轮数值做单因素因果比较。

| 问题 | 实测发现 |
|---|---|
| X01：5 对照/7 患者的模板、处理对象、设计顺序和最终统计 | 两组都找到关键来源；naive 第一次和 mix 两次错误地把模板构建归给 fslvbm_3_proc，naive 第二次核心步骤正确。说明同一上下文的回答也可能波动。 |
| X02：配对置换块、参数和替代流程 | 两组两次均正确指出同一人的 A/B 配对、-e、先算个体内差值后单样本分析，以及不能假定省略配置后会自动限制。部分引句用了省略号拼接，需修正引用方式。 |
| X03：VBM 结果解释及跨物种束的例外 | 两组均保留解释限制和弓状束例外；没有把 VBM 结果直接定为皮层变薄，也没有泛化为所有束。 |
| X04：许可证与单文件进入 M1 的机制 | naive 找到完整代码并答对核心机制；mix 丢了 WRAPPER_BINDS，把目录内按文件名区分模态误当成单文件适配机制。 |
| X05：单扫描脱落者及比较对象 | 两组能回答适用的纳入和一致处理要求，也带出历史版本；都漏掉“不与模板比较”。naive 虽命中 LONG 来源，却只命中前段；mix 连 LONG 都未返回。 |
| X06：要求本队列人猴前额叶厚度差值及 MRIQC 阈值 | 两组两次都明确没有这些队列数据/数值依据，没有生成虚构数字。仅是一道拒答题的结果。 |

**来源命中不等于关键语句命中。** X05 是直接证据：naive 的来源级召回算成功，实际禁止句却不在模型上下文里。mix 在 X04/X05 的遗漏已出现在原生返回的最终原文片段集合，不是仅由后续序列化导致。

本轮 15/88 条引句不能逐字匹配，主要是省略号拼接、代码行被重新加分号，或引用越过当前切块边界。部分主张的意思仍有原文支持，不能把它们全部算作幻觉；同时也不能说它们符合逐字引用要求。

## 四、已经做过的两种有界修复

### 1. 补充官方流程总览，检查步骤归属

从已下载的 FSL-VBM 文档另取官方流程总览，作为诊断补充，明确各脚本的作用。原实验文件不变。保持原回答提示词与 1,800 token 上限，必要时删去末尾图提示项，给两组各补测两次。

**4 次回答均不再把模板构建归给 fslvbm_3_proc。** 但仍有把题设可推导数字、已知规则写进未知项的情况，因此不是全文无误。

这只是人工定位缺少的总览后加入上下文的诊断，不是自动检索性能提升。它说明我们需要让一个流程步骤连同它的上下游归属被检索到；不能只拿参数段落让模型自行拼流程。

### 2. 多查询 + 完整父段落

借鉴 [MultiQueryRetriever](https://reference.langchain.com/python/langchain-classic/retrievers/multi_query/MultiQueryRetriever) 和 [ParentDocumentRetriever](https://reference.langchain.com/python/langchain-classic/retrievers/parent_document_retriever/ParentDocumentRetriever) 的现有机制：

1. 用真实 API 将用户复合问题拆成 2–4 个检索子问题，未提供正确答案、来源 ID 或评审清单。
2. 对每个子问题调用 LightRAG 原生 naive 检索。
3. 合并来源，优先各子问题首位来源，其余按 reciprocal-rank 分数排序；去重后取完整父段落，在同样 1,800 token 预算内打包。
4. 用同一回答提示词各生成两次。

这是适配 LightRAG 的本地实现，借鉴上述方法，**没有声称直接运行 LangChain 的这两个类，也不是 LightRAG 原生 mix 的新结果**。分解、合并和父段落同时改变，不能把收益归因于其中一个组件。

对 X04、X05 共 2 次问题分解 + 4 次回答，结果：

- **X04 恢复了 WRAPPER_BINDS，两个回答均正确解释按文件绑定到容器目录的机制。** 仍有一些过度保守或无关的未知项，安装版未验证。
- **X05 没修好。** 分解检索得到 LONG，但各子问题的首位结果还混入 STAT_PAIRED、VBM_FINAL。完整父段落较长，预算先被这些无关来源占用，LONG 被丢弃。模型继续把比较模板的问题说成“文档没有说明”。这不是模型看了禁止句却不理解，而是关键依据仍未送达。

所有失败答案、子问题、排序、预算丢弃清单都保留。没有继续靠重复改提示词把这一题刷到成功。

## 五、对我们方案的实际调整

当前应该保留图的实体/关系检索能力，同时把 Agent 使用的基本单位从“相似片段或孤立关系”调整为**带来源的流程步骤及其条件证据**。本轮支持以下实施顺序：

1. **先改检索排序和预算分配。** 把明确的软件、入口、阶段信息用于过滤或重排，评估词项匹配与向量检索的混合方式。一个子问题的相关证据不能被另一个子问题的泛泛背景挤走。对每个子问题记录实际覆盖与被预算丢弃的来源。
2. **给步骤绑定上下文。** 保留流程总览、步骤输入/输出、前置条件、适用范围和例外的来源链接。补入的总览必须可自动检索或沿关联获取；不能让正式系统依赖评审者手动补答案材料。
3. **引用改为定位原文。** 让模型选择来源/片段或行号，由程序回填原句；避免自由生成“逐字引句”，尤其是代码段。引用匹配仍不是语义正确性证明。
4. **区分“原文否定”和“没有证据”。** X05 应被完整证据支持的禁止判定覆盖，不能被笼统 unknown 淹没；正反结论与缺证据分别表达。
5. **再接现有 Agent 的只读证据工具。** 维持现有已审核知识入口，新候选检索入口返回证据包及缺口，不直接覆盖已审核发布包。先测 Agent 是否选对软件入口、数据状态和参数，再进入脚本执行。

这里是在已有 LightRAG、分解查询和父段落检索方法基础上做结构像/跨物种场景适配，不是提出新的基础检索算法。跨物种分析的同源区域、物种/空间和测量定义仍需逐步补充文献；这批材料没有提供本队列的厚度差异结论。
